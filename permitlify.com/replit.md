# PermitDaily (Permitlify)

## Overview
PermitDaily (formerly Permitlify) is a platform designed to provide building permit intelligence and AI-scored lead generation for contractors. The project aims to streamline the process for contractors to identify and secure promising leads by leveraging scraped permit data and advanced AI scoring.

## System Architecture

### UI/UX Decisions
The user interface utilizes Django templates with vanilla CSS and JavaScript, employing DM Sans, Plus Jakarta Sans, and JetBrains Mono fonts. The design system features a sticky topbar (60px) and a fixed sidebar (220px) for consistent navigation across all inner-app pages. Color schemes are based on `--pr` #1d4ed8 (blue) and `--ac` #059669 (green), with a blue-to-green gradient. Key UI components include section cards with `border-radius:16px`, stat cards, permit tables with score rings, status badges, and action buttons. Settings are organized into a 5-tab interface, while the user profile includes an avatar card, mini-stats, an activity feed, and forms for personal information and password management.

### Technical Implementations
The backend is built with Django 5.2 (Python 3.11). The system uses Django's file-based sessions stored in the `sessions/` directory. User authentication involves SHA-256 hashed passwords. All protected views are secured with the `@login_required` decorator.

**Feature Specifications:**

*   **Authentication & User Management:** Users are managed in a `users` table with unique emails. A demo user (`mk@permitdaily.com` / `demo1234`) is seeded on startup for testing. **Google Sign-In** is supported via a stdlib OAuth 2.0 "authorization code" flow (`/auth/google/start/` → `/auth/google/callback/`); `google_sub` is stored in the user JSONB and the session is rotated on completion to defend against fixation. Existing email matches are auto-linked the first time, but only when no other Google account is already linked. Admins manage the OAuth client at runtime from `/admin-panel/google-settings/` (toggle + client_id/secret + redirect-URI helper).
*   **Permit Management:** Scraped permit records are stored in a `permits` table, including AI scoring, status, trade, and date information. The system supports filtering and displaying permits based on various criteria. The `/permits/` page uses **DataTables server-side processing** backed by `permits_data_view` (`core/views.py`) → `query_permits_for_dashboard()` (`core/db.py`); all filters, sort, and `LIMIT/OFFSET` are pushed into a single parameterised SQL query so accounts with thousands of permits stay fast. The user's city subscription set is the first WHERE clause on every query, which preserves per-city authorisation regardless of any panel filter the client sends. Sort columns are whitelisted (no SQL injection from `order[0][column]`). The legacy 2,000-row in-memory cap and yellow truncation banner have been removed; the view caps `length` at 500 per request as a defence-in-depth limit.
*   **Notifications System:** A database-backed notification center allows users to manage and receive alerts. Notifications are paginated, filterable by type, and can be marked as opened. Users can configure delivery preferences and channels (Slack, generic webhooks).
*   **Support System:** A full ticketing system is integrated, allowing users to create and track support tickets. It includes a user-facing interface for ticket creation and thread viewing, and an admin panel for managing tickets.
*   **API Portal:** An agency-only API portal provides per-user API key management, a playground for testing endpoints, and usage statistics. It supports various filters for permit data retrieval, mirroring the web interface.
*   **CRM Integrations:** The system supports integrations with HubSpot, GoHighLevel, and Zapier via OAuth 2.0 for HubSpot and GHL, and a webhook for Zapier. These integrations are agency-gated and allow for managing CRM connections and pushing data.
*   **Billing Receipts (Whop):** Branded payment-success / activation emails are dispatched through `_maybe_fire_payment_success_email` (`core/views.py`), called from BOTH the synchronous post-checkout redirect (`ls_success`) AND the async `membership.went_valid` webhook branch in `ls_webhook`. Dedup is per `(user_id, membership_id, plan)` tuple, stamped on the user JSONB as `payment_email_last_membership` / `payment_email_last_plan` — whichever path wins the race fires the receipt and stamps; the other path sees the stamps and silently no-ops. The webhook path guarantees delivery when the user closes the browser before the redirect runs, an upgrade happens off-platform from the Whop dashboard, or `ls_success` membership verification fails. The (mem_id, plan) tuple (not just mem_id) means a real plan change on the same membership re-sends, while routine renewals (Whop fires `went_valid` every billing cycle) do not spam the user. Test coverage in `core/tests/test_payment_email_dedup.py` (6 tests).
*   **Admin Blog Editor:** Authors run an AI-assisted publishing flow at `/admin-panel/blog/` — list posts (search + paginate), then in the new-post editor paste a source URL → AJAX scrape via Firecrawl → AJAX rewrite via Claude (returns one JSON post object) → review/edit form → Publish. AI keys (`firecrawl_api_key`, `claude_api_key`, `claude_model` — default `claude-sonnet-4-5-20250929`) live in the `system_settings` table and are managed at `/admin-panel/blog-settings/`. Both vendor clients are stdlib `urllib`-only (no new deps). All endpoints `@admin_required` + CSRF-protected. **Body is always HTML:** the Claude rewrite prompt requires HTML output, and `core/blog_ai.py:md_to_html()` (idempotent, stdlib-only) is run at AI-rewrite time **and** at render-time inside `blog_post()` so legacy markdown bodies can never display raw `## headings` or `**bold**` literals through `{{ article.content|safe }}`. The `.prose-article` styles in `templates/core/blog_post.html` give published posts a magazine-style long-read look (lede paragraph, gradient-bar H2s, custom bullets/numbered counters, pulled-quote blockquotes, three-dot HR).

### System Design Choices

*   **Database Schema:** The primary database is Supabase Postgres. Tables (`users`, `banned_emails`, `sessions`, `login_history`, `system_settings`, `support_tickets`, `notifications`, `invoices`, `permits`) utilize a `JSONB data` column for flexible storage, along with materialized columns for frequently queried data.
*   **Permit Ingest API:** A dedicated endpoint (`POST /api/v1/permits/ingest/`) handles the ingestion of permit data from scrapers. It supports bulk upserts and uses an `X-Scraper-Key` for authentication. The upsert operation is non-destructive on partial payloads.
*   **Scrapers list DataTable (May 2026):** `/admin-panel/scrapers/` is now a server-side jQuery DataTable mirroring the per-scraper detail page theme. Shell view `admin_scrapers_view` seeds the toolbar (search box, **State** dropdown with `(count)` per state, cascading **City** dropdown driven by `window.SC_CITIES_BY_STATE`, total scraper count); rows fetch via `GET /admin-panel/scrapers/data.json` (`admin_scrapers_data`) which honours the standard DataTables params (`draw` / `start` / `length` / `order[0][column|dir]`) plus our own `q` / `state` / `city` filter params. Backend pagination/filter/sort lives in `core.db.list_scrapers_dt(*, search, state, city, start, length, order_col, order_dir) -> (rows, total_unfiltered, total_filtered)` with a strict whitelist `order_map` mapping the 7 sortable columns to safe SQL fragments — direction is always coerced to `ASC|DESC` and `NULLS LAST` is appended *after* the direction. `core.db.list_scraper_state_city_options()` powers the dropdowns in one cheap query. The legacy `list_scrapers()` is kept for the cron caller. The "**+ New Scraper**" form (`admin_scraper_new_view`, template `admin_scraper_new.html`) gained a **State** `<select>` (full US states from `core.us_cities_top.US_STATES`) and a **City** input backed by a `<datalist>` cascading from `window.NW_CITIES_BY_STATE` — both fields are optional, accepted on POST/GET (`state` validated to 2-letter alpha, city titlecased), passed through to `create_scraper(city=, state=)` which stores them on the scrapers row so the new dropdowns populate. Existing scrapers were one-shot backfilled by parsing the trailing `" ST"` token out of `name` (10/11 rows matched). New URL `path('admin-panel/scrapers/data.json', …)` is registered **before** the `<int:sid>` patterns so it can't collide with `/admin-panel/scrapers/<sid>/`.
*   **Per-scraper Firecrawl-Agent Run-now (May 2026):** The `/admin-panel/scrapers/<sid>/` page now ships a **Firecrawl-Agent settings card** above the permits table — toggle (`Use Firecrawl Agent for Run now`, default ON), prompt template (8000-char max, supports `{url}`/`{city}`/`{state}`/`{date_from}`/`{date_to}` placeholders), model dropdown (`spark-1-mini`/`spark-1-pro`), `max_credits` per run (default 1500, hard-capped 50000), Save / Reset buttons. Settings persist into `system_settings` keys `accela_scraper_agent_prompt_template` / `_model` / `_max_credits` / `_settings_saved_at` / `accela_scraper_use_agent` via `POST /admin-panel/scrapers/agent/settings/` (`admin_scraper_agent_save_settings`, JSON-only, full validation, mirrors finder). When the toggle is ON, **`mode='single'`** runs branch into `_run_agent_branch()` in `core/scraper_accela.py` which sends ONE prompt to Firecrawl Agent SDK — the agent is responsible for browsing the list, opening each detail page, and returning structured rows; results stream back via Pydantic `AgentPermit/AgentResponse` schema and are upserted row-by-row with progress steps; legacy capID3 backfill (`mode='backfill'`) is unchanged. **Cross-source dedup:** new `permits.dedup_hash TEXT` column + partial unique index `permits_dedup_hash_uq WHERE dedup_hash IS NOT NULL`, computed by `compute_permit_dedup_hash()` in `core/db.py` (SHA-256 of normalised permit_number + state + city + address + trade + contractor_name + contractor_email + contractor_phone + issued_date + valuation_cents — only emits a hash when `permit_number` plus ≥1 of address/contractor_name/email/phone are present). The `_norm_for_dedup()` helper guarantees explicit equivalence classes so cross-source rows actually collide: `None`/`''`/`'  '`/`0`/`'0'`/`0.0`/`'0.00'` all collapse to `''`; bools never alias to `'1'`; integer/float/string-numeric (`1500`, `1500.0`, `'1500'`, `'1500.00'`, `'1,500'`, `'$1,500.00'`) all hash as `'1500'`; `date(2026,4,1)` and `'2026-04-01'` both reduce to `'20260401'` after the alphanum collapse; negative numerics drop sign so int/string forms agree. `upsert_permit()` stamps the hash on every write; if the partial-unique index fires (`psycopg_errors.UniqueViolation` on `permits_dedup_hash_uq`) the function falls back to **UPDATE BY hash** which preserves the original row's `source` / `source_permit_id` lineage so the same physical permit doesn't multiply when picked up by both the legacy and agent paths. Backfill helper `scripts/backfill_permit_dedup_hash.py` is idempotent + batched, handles cross-source collisions during backfill by leaving the loser at NULL. New supporting indexes `permits_permit_number_lower_idx` / `permits_contractor_email_lower_idx` / `permits_contractor_name_lower_idx` for the case-insensitive dedup lookups.
*   **Accela Scraper System:** End-to-end permit ingestion built around Firecrawl + Claude AI. Two new tables (`scrapers`, `scraper_runs`) record configured Accela CapDetail URLs and per-run progress. Admin pages live under `/admin-panel/scrapers/`: list (search + pagination), `new/` (URL parser preview, accepts `?url=…&name=…` GET params for pre-fill), `<sid>/` (header + filters bar [date / has_email / has_phone / search] + paginated permits + recent runs sidebar + Run-now/Backfill buttons), `<sid>/run/` (sync POST), `<sid>/backfill/` (async POST → daemon thread, progress modal polls `/scrapers/runs/<rid>/status/`), `<sid>/delete/`, plus standalone `/admin-panel/scraper-stats/` (30-day chart + summary cards), `/admin-panel/scraper-settings/` (Firecrawl + Claude keys + cron toggle — keys SHARED with Blog AI via `system_settings`), and `/admin-panel/scrapers/accela-search/` (Accela permit-search **finder**: top card exposes the **Firecrawl Agent settings** — prompt template with `{city}`/`{state}` placeholders, model dropdown [`spark-1-mini`/`spark-1-pro`], `max_credits` per city [default 500, **no server-side upper cap** — admin asked for the freedom to push 5000/50000+ since Firecrawl already enforces the per-account budget downstream; only `max(1, …)` is enforced server-side and the template input has `min="1"` with no `max=` attribute. Defaults were raised from 100/1000 because the agent typically needs ~150-400 credits per city to converge, and a 100-credit cap caused most cities to fail with "Agent reached max credits"]; when an agent run exhausts the per-city budget the error is rewritten to a friendly hint pointing the admin at the settings card, and each row's log shows `credits_used / credits_budget` so it's obvious when the budget was the limiting factor; the settings card also has a **Save settings** button (POST `/admin-panel/scrapers/accela-search/settings/`) that persists the prompt template, model and max credits into `system_settings` keys `accela_finder_prompt_template` / `accela_finder_model` / `accela_finder_max_credits` (+ `accela_finder_settings_saved_at` for the "Last saved …" status), and a **Reset to defaults** button that rolls the form back to whatever was rendered; below that a state dropdown → editable city list from `core/us_cities_top.py` → per-city call to `Firecrawl.agent(prompt=…, schema=AccelaSuggestion[Pydantic], model=…, max_credits=…)` which browses autonomously and returns structured `{url, confidence, reason}`; defence-in-depth re-validates the host is `accela.com` / `*.accela.com` server-side; results table has View-link + Add-to-scrapers buttons that open the `new/` form pre-filled in a popup, plus a per-row collapsible **Firecrawl log** showing agent status, credits used, model, agent id, prompt sent and raw response data; every agent call is logged under `source='accela_finder'` mode `'agent'` so it appears in the Firecrawl Usage dashboard). The pipeline (`core/scraper_accela.py`): `firecrawl_scrape()` calls Firecrawl with `waitFor=3000` + a `wait` action so .NET WebForms JS finishes rendering, then `claude_extract()` runs a strict extraction prompt with one-shot example to produce a flat permit JSON with AI score/grade/tier; `_normalise_permit()` coerces phone to `(NNN) NNN-NNNN`, email to lowercase-validated, dates to ISO, state to 2-letter; `_validate_and_register_city()` auto-adds new (city, state) pairs to `supported_cities`; `upsert_permit()` writes with `source='accela:<scraper_id>'` and a stable `source_permit_id=agencyCode-capID1-capID2-capID3` composite. Background runs use `threading.Thread(daemon=True)` (no Celery), updating `scraper_runs.processed/succeeded/failed/current_step/error` so the modal can render a progress bar. Daily cron is `scripts/run_scrapers.py` — wire it to a Replit Scheduled Deployment (e.g. `python3 scripts/run_scrapers.py` on a `0 9 * * *` schedule); the `scrapers_cron_enabled` system_settings flag lets admins pause ingestion without un-scheduling the job.
